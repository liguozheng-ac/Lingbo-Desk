# 角色旁文字聊天框卡顿与退出：排查记录（未解决）

> 2026-11-17 发布说明：本文保留各排查阶段的历史状态；文中的“未推送 GitHub”指当时尚未推送。本次仅同步源码和记录，日常安装版仍为 0.3.7，未将桌面卡顿标记为已修复。

日期：2026-11-16。安装版 0.3.7。

## 用户报告与范围

用户明确报告角色旁的文字聊天框在键入时十分卡顿，随后程序退出；并非发送后等待模型。获准在历史数据副本中复现、记录输入表现与退出原因，定位后针对性修复，验收通过后再更新安装版。

## 已确认的事实

- 初查时安装版进程和后台均已停止。原始任务仍为暂停、版本 1，两份输入来源和零条执行回执保留。
- 现场已有日志包含 `gateway.closed`、`ok: true` 与桌面服务正常停止记录。本次未取得能确定退出起因的 Windows 故障事件或崩溃转储。这只能证明走过清理流程，不能排除异常触发退出。
- `components/scenarios/chat/components/history.vue` 已使用虚拟列表，不能直接推断“消息多且全部渲染”是根因。`use-chat-composer.ts` 的草稿是本地浅引用，代码不支持“每键都请求 DeepSeek”的说法。
- 在隔离副本启动实际安装程序；原始用户目录没有交给测试程序使用。副本未复制云服务凭据，关闭副本的 MCP。测试期间没有发送用户消息、调用模型或执行原任务。

## 测量与边界

本机忽略目录 `artifacts/chat-input-diagnosis` 保存探针、隔离配置副本和结果，不发布原始日志及配置。

一次旧会话页面的 80 次合成 `input` 检查完成：每次设置文本后等待两个动画帧；中位数 26.5 ms、95 分位 56.7 ms、最大 77.9 ms，总计约 2.11 秒，没有观察到 Long Tasks 条目。该数值包含双动画帧等待，不能视作物理键盘延迟，也不证明中文输入法不卡顿。

自动化真实点击遇到透明窗口穿透、焦点不一致；部分页面加载或调试请求超时。它们属于诊断过程的不确定因素，尚不能归因为产品故障。一次中文文本注入最终在副本草稿中读到 33 字符，但未获得可靠的键入到显示时间，不计作顺畅性验收。

新旧会话对照与长文本粘贴检查未完成：探针等待过程中被正常退出打断，最终结果为页面关闭错误，没有可用的对照统计。不能声称这些检查通过。

问题仍未解决。下一阶段需先补充有界、不会依赖隐藏窗口动画帧的监测，再在前台用真实中文输入法复现，并同时记录窗口焦点、主线程延迟与退出事件。取得可重复证据后才决定调整输入框布局、窗口穿透或其他模块，不能将任一候选直接写成根因。

## 后续阶段：已实现监测，等待真实键入

新增 `desktop/launcher/chat-input-monitor.mjs`。打包启动器仅在显式设置 `LINGBO_INPUT_DIAGNOSTICS=1` 时开启；默认关闭。当前日常安装版尚未升级；本机隔离观察器将同一份模块加载到实际 Electron 应用的主进程，等待手动操作。

- 只观察本机指定渲染来源下的 `/chat` 与 `/chat-floating`，不观察配置页、其他站点或密码输入框。
- 只统计可信键盘/输入事件的次数、组合输入次数和持续时间、焦点与可见性、事件处理延迟、输入事件到后续动画帧的等待，以及长任务的次数和时长。
- 不读取或记录草稿值、按键名称、组合输入文本、聊天正文、截图、文件路径、会话 ID 或凭据。新事件经 `diagnostic-privacy.js` 的数值与枚举白名单过滤。
- 最多保留 64 个帧样本；同时只有一个帧等待，设 1 秒超时。失焦或隐藏时丢弃等待，不把后台节流算作前台输入延迟。
- 主进程每 5 秒取一次快照，超时 2 秒记录一次；未结束的请求不重叠追加。原生窗口无响应、渲染进程退出、子进程退出和应用正常退出另记固定事件。监测不重载页面、不重新执行任务，也不改变鼠标穿透或计时节流。

验证：3 项新增 Node 测试覆盖来源隔离、超时不重叠、切页后的过期结果丢弃、清理和隐私过滤；使用安装版配套依赖及 Python 完成 142 项后端检查。独立 Chrome 中另有 5 组监测器检查通过：可信键入、排除非可信合成输入、排除密码框、帧停滞只产生一个超时、清理后重装。浏览器注入字符不等于真人中文输入法验收。

全量测试最初因本机测试环境缺少 Python 包和源码依赖失败，改用安装版已有的配套 Python 与依赖后通过；未改变用户的 Python 全局环境。

隔离观察器曾两次等候聊天框加载超时并正常关闭；尚未确定这是产品问题还是调试启动条件导致。最终观察器保留监测，但不自动打开聊天或注入文本，由用户手动打开、键入并观察。它没有复制服务凭据或任务目录，MCP 在副本关闭；勿在副本发送消息或执行任务。真正需要保存的数据仍以日常安装版为准。

监测采样描述的是事件处理与帧调度，不是硬件键盘到屏幕的完整延迟；组合输入持续时间包含用户选词时间。是否由某模块造成卡顿，仍须结合这次真人复现结果判断。未将原问题标记为修复，也未发布 GitHub 或安装升级。

## 常规启动对照：已启动，待用户反馈

用户补充：A（打开聊天）、B（输入框聚焦）、C（中文输入）及 F（滚动、菜单等操作）均卡，仅隔离测试版出现；还发生鼠标被工作台占用、窗口持续拖动和难以操作其他软件。该反馈不能缩减为单一文本输入性能问题。

后续经确认改做普通启动对照。用未修改的日常安装程序、冷复制的角色配置与缓存、独立用户目录启动。进程命令行仅为程序路径，没有 debugger、remote-debugging、自动化连接、注入监测、IPC 控制通道或自动键鼠输入。启动准备脚本退出后不保留控制循环。

用户先关闭新工作台窗口，仅保留角色和聊天，手动检查打开、聚焦、中文输入、滚动与鼠标切换；结果尚待反馈。这一对照同时消除了调试连接、监测注入、冷缓存和额外配置窗口等差异，即使恢复顺畅，也不能直接将原因归给其中一个变量。逐项验证依赖该反馈，当前不加监测或自动控制。

### 对照反馈与下一项检查

用户反馈常规启动副本“不是很流畅但是已经正常切走了”，随后明确剩余最明显的是打开聊天框或点击输入框慢。此反馈支持该样本未再出现之前严重的鼠标占用，不能记作所有卡顿解决。

没有附加调试器、注入监测或输入控制，仅通过操作系统对进程取了约 2 秒的 CPU/工作集快照：桌面主进程与多个渲染进程占用较高，网关相对低。读数以单个 CPU 核心为 100%，允许多线程进程超过 100%；没有固定用户操作、后台负载和窗口可见性，不作性能基准，也不凭此确定具体函数。原始数据为本机 `artifacts/window-baseline/.../os-sample-1.json`。

已核对源码：默认悬浮聊天创建透明、无原生边框的窗口，初始启用鼠标穿透，页面按光标命中位置切换；经典聊天在 Windows 下使用普通窗口，不走该悬浮穿透路径。两者仍共用会话、对话组件与部分通信服务。因此下一项让用户通过已有“聊天窗口样式 → 经典窗口”切换，仅变更副本中的窗口模式，对比打开与聚焦。该对照结果尚待用户反馈，不将透明窗口先行定为根因。

### 角色找回：样式对照尚未执行

用户在切换前反馈找不到数字人。原生窗口检查明确返回主角色窗口已最小化；恢复该窗口后观察到空白，角色心跳仍断开，因此不能把最小化视作全部原因。现有普通启动日志未提供明确的渲染丢失原因，尚不能确定崩溃、资源或其他因素。

通过第二次启动同一个隔离目录唤回已有工作台，再用工作台内置 Ctrl+Q 正常退出；确认旧进程结束后，用相同副本、相同配置普通重启，没有调试参数或监测注入。此处仅执行一次正常退出快捷键与原生恢复操作，没有鼠标拖动测试。随后窗口截图确认原创 B 再次显示，角色心跳恢复，模型请求数为 0。

角色恢复已确认，经典窗口的流畅度仍未验收。本次重启不能记作原始卡顿或渲染丢失根因已修复。日常安装程序与日常配置保持不变。
