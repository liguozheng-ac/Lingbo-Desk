## 浏览器问题的更正

之前把 `test-action-contract.js:178` 的失败简称为“大浏览器分类缺陷”，这个判断不够准确。`engine/src/capabilities/tools/browser-display.js::execBrowserSetDisplayMode()` 明确返回 `BROWSER_DISPLAY_REMOVED`，该工具不再向模型公布；旧测试却仍要求它成功完成卡片/大窗切换。不能通过恢复停用工具让测试变绿。

本轮改动：

- 更新旧模式、旧回复和旧浏览器关系断言，验证纯显示模式要求不创建已停用工具的执行契约；兼容调用仍明确返回移除原因。
- `engine/src/runtime/action-contract.js::classifyDirectBrowserAction()` 保留正常 URL 导航，不再因同时提到旧显示模式而拦截；支持“请用你的浏览器打开 URL”这一明确前缀，仍检查目标 URL。
- `actionContractCompletionIssue()` 拦截兼容打开工具对 Safari、系统默认浏览器及旧卡片/大窗关系的错误完成描述。`verifiedActionContractReply()` 使用选定 Chrome Agent Window 的实际分支语义。
- 完整 `test-action-contract.js` 通过；没有跳过后续截图、交付和工具执行约束。

这里修的是引擎保留的浏览器兼容分支。**产品当前后台工作使用 `backend/work-browser.mjs::WorkBrowser` 的独立 Edge**，本轮没有增加 Chrome 依赖或实现新的窗口大小切换功能。

## 长文档读取与替换

修改前用合成 DOCX 复现：超过 60000 字符后，即使传 offset，也会在旧 `documents.py extract` 路径被提前拒绝；替换会把制表符两侧的文字拼成连续目标；嵌套文本框会进入外层和内层段落的重复匹配。最初 4 项测试中 1 通过、3 失败，原日志保留。

| 代码 | 当前行为 |
| --- | --- |
| `backend/documents.py` 的 `extract` | 报告导入继续限制 60000 字符 |
| `extract-window` | DOCX/PDF 本地正文最多 1000000 字符，只返回指定 offset/limit、总长度及截断状态；单窗口最多 20000 字符 |
| `extract-check` | 在本地返回受限完整正文，用于验收；不自动发送给模型 |
| `backend/work-tools.mjs::WorkTools.execute` 的 `work_read` | 将范围传给文档提取器，避免提取后再次按 offset 截取；云模型每次最多读取 20000 字符，本地模型 6000，累计上下文预算继续为每次执行 50000/12000 |
| `WorkTools.acceptanceText()` | DOCX 完整正文检查上限扩至 1000000 字符；保留文件大小、授权、SHA256 及取消检查 |
| `backend/work-office.py::edit_docx` | 只替换正文段落/表格中的连续文字，保留其他 ZIP 部件；制表符、换行不再被当作无间隔连接；目标涉及文本框、动态字段、修订或内容控件时整项拒绝，不输出部分修改结果 |
| `backend/work-schema.mjs` | 明确告知模型范围读取、读取预算和 DOCX 修改边界 |

这不是流式 XML 解析：完整提取仍在本机进行，再返回小窗口。既有文件的修改仍要求 SHA256、具体确认和备份；报告导入没有放宽到百万字符。DOCX/PDF 窗口 offset 按 Python 的 Unicode 字符计数；普通文本既有实现使用 JavaScript 字符串索引。跨格式自行计算偏移时需留意 emoji 等字符的差异。

“结构保留”的证据是非文字 XML 与其他 ZIP 部件不变。替换文字继承首个匹配片段的样式，不保证跨不同字体片段的逐字符样式、分页或视觉版式完全一致。页眉页脚保留原样，文本框/字段/修订等目标会明确拒绝。本轮没有增加 Excel/PPT 正文验收器，也不宣称支持任意复杂 Office 文档。

## 真实模型长 Word 验证

`scripts/evaluate-long-document.mjs` 使用真实 DeepSeek、真实工作进程、文件 broker 和 Python 适配器。生成 **153620 字符** Word，含分散段落、不同样式 run、表格、图片、页眉和页脚；原件目录只授予读取权限。

模型按指定范围读取目标 → 复制到任务产物 `edited.docx` → 读取副本 → 精确修改“待改,”为“已改，” → 验收副本。测试程序只批准本轮明确指定的**合成副本、原文、新文和对应哈希**，其他确认一律拒绝；没有绕过产品的确认接口。

通过的这次运行：

- 用时 **14.797 秒**，7 次工具调用，模型累计读取正文 **280 字符**。
- 8 次实际模型请求，返回的输入 usage 合计 **32209 tokens**、输出 **1584 tokens**。读取正文少不等于请求没有系统提示及工具 schema 开销。
- 原件 SHA256 和修改时间未变；副本正文符合精确修改，其他 ZIP 部件逐项字节相同，去除文字后主文档 XML 结构相同。
- 正式完成条件来自任务提交时的 contains/notContains，完成后实际重新提取全文验收。

首次评测脚本误用了不存在的 `/work/approval`，在确认环节返回 404；该次任务取消，保留失败日志。改为产品实际的 `/work/approve` 后重跑通过。失败运行已发生 4 次模型请求，输入 11958、输出 587 tokens，不能忽略这部分用量。两次共观察到 12 次模型请求；货币费用没有账单证据，仍标为未知。

这是一个指定局部修改的成功样本，不是长文档任务总体成功率，也没有重放历史“请求过大”的原始失败请求，不宣称已经消除全部上下文溢出问题。测试没有打开 WPS 或验证 WPS 界面操作。

## 四组故障恢复

`scripts/verify-work-recovery.mjs` 使用独立网关、实际 fork 的工作进程和真实文件操作；模型回答为固定测试响应。所有测试都检查原产物 SHA256/修改时间、被跟踪 worker 退出及最终网关正常关闭。

| 故障 | 实际验证结果 |
| --- | --- |
| 上游请求断连 | 已有写入不被记为任务完成；故障后可人工继续，读取已存在产物后完成，没有重复写入 |
| 网关被强制结束，写入已有回执 | 重启读取状态为中断，不自动请求模型；人工继续后使用已有回执完成，成功修改回执仍只有一次 |
| 文件已写入但回执未落盘 | 重启保留 intent 并标为不确定；未人工核对的恢复请求被拒绝，不自动重放或补造回执 |
| 任务 JSON 损坏 | 原文件保留，界面返回警告，不加载为可执行任务、不自动修复或执行；已有产物不变 |

没有断开整台电脑的网络或强制电脑睡眠。上游故障通过测试服务注入；网关崩溃通过结束本次创建的进程注入。已有恢复机制在这些场景表现正确，本轮没有为制造改动而重写状态机。

这不等于任意真实模型都不会提出重复动作，也不保证清理任意脱离的脚本后代。Windows Job Object、长时间运行、真实睡眠/唤醒、掉电/磁盘故障仍未验收。
