# 已有任务产物导出修复与验证

日期：2026-11-19。范围：将同一会话中已完成任务的指定产物，经过具体确认后复制到已授权资料文件夹。修复日常安装版；没有发布新版本号、重建 NSIS 安装器或推送 GitHub。

## 原因与原有边界

原复制任务前三次执行均暂停：来源文件实际存在，但 `WorkPolicy.resolve()` 只允许任务访问自己的内部产物目录。其他任务产物位于受保护的本地数据目录，普通 `work_list` / `work_copy` 无权读取。目标桌面资料文件夹只有读授权，也不能接受普通复制工具的写入。

“继续执行”会重启执行器，不会改变目录授权或任务绑定的授权 ID；再次点击无法解决这个缺口。把整个内部数据目录加入授权也不是正确修复：该目录包含配置、会话和其他受保护数据。

原验收只检查固定名称的 Markdown 文件，没有覆盖 DOCX，且与“同名另存”的用户要求不完全一致。

## 实现与调用链

1. `backend/work-schema.mjs` 注册 `work_artifacts` 和 `work_export`，桌面桥接的 schema 同步更新。
2. `WorkService.run()` 向真实工作进程说明产物导出规则；模型获得工具定义后选择调用。
3. `WorkService.execute()` 保持工具白名单、任务票据、顺序执行及调用次数限制，将这两个工具分派到 `backend/work-artifacts.mjs::executeArtifactTool()`。
4. `work_artifacts` 通过 `WorkService.find(job.sessionId, sourceTaskId)` 验证归属，只列出已完成且状态确定的其他任务的直接文件。文件必须有匹配当前 SHA256 的成功文件动作回执。
5. `work_export` 预先确定来源、SHA256、目标目录和具体副本名称，再进入现有 `confirmation()` / `approve()` 流程。
6. 确认后再次检查来源、授权、路径链接和目标冲突；保存执行意图，使用 `COPYFILE_EXCL` 复制，核对来源与副本哈希，由执行服务持久化动作回执。
7. `work_finish` 继续核对动作证据和固定验收条件；工作台依据实际回执显示导出位置。

来源必须是任务 ID 加单个文件名，不能传入任意内部路径、子目录或 Windows 数据流。不会让普通文件工具获得其他任务目录的访问权。

目标仍须在当前任务绑定的有效资料文件夹授权内。有效读授权加此次具体副本确认，可以完成这一项导出；不会把文件夹升级为持久写授权。授权 ID 已失效的旧任务仍须按现有授权流程处理。

同名目标按 `(1)`、`(2)` 等另存。确认等待期间出现新的同名文件时直接拒绝，不会自动换成用户未审核的路径。拒绝导出会记录到当前任务版本，模型不能在同一版本换名重复请求。

## 验收与界面

- `allowRename` 默认为关闭。只有用户允许同名另存、且任务提交或暂停修改时显式开启，验收才沿当前版本成功 `work_export` 回执的 `requestedPath` 查找实际副本。普通精确路径验收保持原规则，`work_finish` 不能改写条件。
- `needs_input` 的具体原因进入暂停错误提示；旧任务已有的暂停说明也会显示在错误区域。“已请求继续执行”同时说明实际状态和权限不会自动变化。
- 确认卡展示实际目的路径、来源及哈希；结果区显示外部副本的位置。不会把外部副本伪装成本任务内部下载文件。
- 打包清单新增 `backend/work-artifacts.mjs` 哈希。
